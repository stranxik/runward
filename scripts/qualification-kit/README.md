# runward {{VERSION}}: qualification kit

**Read this first.** This kit is material to help you produce your own tool qualification or tool
confidence work, in your context of use. runward does not determine a TQL, a TCL, a tool class or a
validation outcome for anyone, and no body has assessed runward or this kit. The report the runner
writes records what the tests did on your installation; what that is worth in your process is your
determination, and your assessor's.

Built from commit `{{COMMIT}}` of github.com/stranxik/runward (ADR-0087).

## What is in it

| Path | What it is |
|---|---|
| `run.mjs` | The runner. Node only, no dependency. |
| `tests/` | The test files the requirements document cites, `smoke.js` and the attack corpus `audit-corpus.js`, as they are at the source commit. |
| `docs/tool-operational-requirements.md` | The requirements of this version: each one states what the tool must do, the test that exercises it, and what a pass does not assert. |
| `docs/open-anomalies.md` (and `.json` when generated) | The defect register's entries still open for this version, generated by `scripts/open-anomalies.mjs`. |
| `docs/attack-corpus.md` | What the attack corpus is, and what its result measures. |
| `docs/qualification/` | Skeletons for your own documents, when this version ships them. |
| `kit-manifest.json` | The version, the SHA-256 of every file of this kit, the SHA-256 of every file of the npm tarball of this version, and, per cited case, its kind and whether it can run on an installation. |

## Before you run it

Verify the kit file you downloaded, as you would verify the tarball (see `docs/verifying-a-release.md`
in the repository): the kit is attested by the same release chain.

```sh
gh attestation verify runward-qualification-kit-{{VERSION}}.tgz --repo stranxik/runward \
  --signer-workflow stranxik/runward/.github/workflows/build-and-attest.yml
tar -xzf runward-qualification-kit-{{VERSION}}.tgz
```

You need Node.js (22.12 or later, as runward itself) and `git` on the PATH: several tests build
missions in temporary git repositories.

## Run it

Install runward {{VERSION}} the way your project uses it, then point the runner at that installation:

```sh
node runward-qualification-kit-{{VERSION}}/run.mjs --package node_modules/runward
```

Options: `--out <dir>` (default `runward-kit-report-{{VERSION}}` in the current directory), `--jobs <n>`
(test files run in parallel), `--work <dir>` (keep the work directory instead of a temporary one).

What it does:

1. Checks the kit's own files against `kit-manifest.json`.
2. Refuses an installation that is not runward {{VERSION}} (exit 2): the kit runs only against its own
   version.
3. Compares the SHA-256 of every installed file with the attested tarball's list. On any difference
   (a changed, missing or extra file; `node_modules/` is not compared) it records the comparison,
   runs nothing and exits 3.
4. Copies the tests into a temporary work directory and links your installation's `dist/`,
   `templates/`, `regimes/` and `examples/` beside them (files such as `package.json` are copied). The
   tests run your installed code; nothing is written into your installation, and the runner compares
   its digests again after the run to show it.
5. Runs every cited test file, then `smoke.js`, then the attack corpus.

Exit codes: 0 every case that runs here passed; 1 at least one failed (or the installation changed
during the run); 2 usage error or another version; 3 the kit or the installation differs from the
manifest.

## Reading the report

`qualification-report.json` and `junit.xml`, in the output directory. Per requirement: its id, the
cited test, the kind of the test, the result and the duration. Per run: the runward version, Node,
the OS and architecture, the `git` version, and the digest comparison before and after the run.

- **Kind.** `interface`: the test reaches runward only through the `runward` binary (exit codes,
  output, files written). `internal`: the test calls a compiled module of the package (`dist/lib/`)
  somewhere, fixture included; these modules ship, but they are not a public interface. `static`: the
  test reads files as text. The kind is derived by the kit builder from the test source; where it
  cannot tell a fixture from an assertion it says `internal`, never `interface`.
- **not-run-here.** A test that reads the repository's own files (workflows, `docs/`, `src/`, the
  checkout's `node_modules`) cannot run on an installation. It is listed with what it reads and a
  pointer to the `reports/junit.xml` committed at the source commit, which recorded its run in the
  repository. It is never counted as passed.
- **skipped.** `smoke.js` checks that the phase skills' frontmatter parses as strict YAML with
  `js-yaml`, a development dependency the kit does not carry. The runner removes that one check from
  its working copy of `smoke.js` and reports it as skipped (ADR-0087, decision 3). Every other check
  of `smoke.js` runs.
- **The attack corpus** is a regression result on a fixed set of known vectors, each one a defect
  that was found and fixed, in both directions (missions that must be refused, missions that must be
  accepted). It is not a detection rate on vectors nobody has found.

The report is not signed: runward holds no key (ADR-0087, decision 7). If your process needs a signed
record, sign the report with your own identity.

## What a full pass does not tell you

That the requirements are the right ones for your use, that a test is relevant to the requirement it
is cited for (the repository checks that each citation exists, never that it is relevant), or that the
tool will behave the same on another installation. The requirements document states, per
requirement, what a pass leaves open. Read the open anomalies before you rely on a behaviour.
