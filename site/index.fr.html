Après la spec · Livrer et faire tourner

Votre spec a survécu à l'implémentation. Survivra-t-elle à la production ?

Runward est un framework de livraison pour systèmes agentiques : le plancher d'abord, l'évolution sur preuve, la gouvernance dès le jour zéro, la passation avec preuve. Il commence là où le développement piloté par la spec s'arrête.

$npx runward init

v0.5.0 · MIT · publication npm à venir : installez depuis les sources dès aujourd'hui

Pourquoi · Quatre hypothèses rompues

Les systèmes agentiques cassent les règles sur lesquelles l'ingénierie classique s'est construite.

Quatre hypothèses de l'ingénierie distribuée cessent de tenir le jour où un modèle s'installe au cœur de votre système.

01

Le cœur est non déterministe

Même entrée, sortie différente, par conception. Les tests fondés sur la répétabilité ne mesurent plus ce qui compte.

02

L'entrée est indiscernable de l'instruction

Tout ce que le modèle lit peut tenter de le commander. L'injection de prompt est structurelle, pas un bug à corriger.

03

L'oubli devient un problème d'ingénierie

Une mémoire qui ne fait que croître noie le signal. Décroissance, invalidation, consolidation : cela se conçoit, cela ne s'espère pas.

04

Le rayon d'impact est inédit

Un agent outillé agit sur le monde. Une mauvaise sortie n'est plus seulement une mauvaise réponse.

Ce qu'est Runward

Ni un agent, ni un runtime.

Runward est une méthode rendue exécutable. Votre spec existante devient l'entrée de runward/framing.md, et les gates continuent à partir de là.

  • 01

    Une structure de mission en markdown, qui vit dans votre dépôt : cadrage, architecture, décisions, gouvernance, runbook.

  • 02

    10 workflows exécutés par votre agent de code : Claude Code, Cursor, Copilot, Gemini CLI, Windsurf, ou tout agent qui lit AGENTS.md.

  • 03

    48 règles de craft que l'agent applique en construisant : scoring de mémoire, retrieval étagé, event sourcing, fallback multi-fournisseur, défenses contre l'injection de prompt.

  • 04

    Une matrice de 22 arbitrages : chacun avec un défaut sobre et un déclencheur explicite. Pas de déclencheur, pas de complexité.

  • 05

    Une CLI qui audite les gates : runward check dit quel livrable, attendu à quelle phase, est manquant, entamé ou rempli.

  • 06

    Un plancher de référence TypeScript clonable : cœur hexagonal, modèle derrière un port, chaîne de middleware, plafond de coût dès le jour zéro. Zéro clé, zéro réseau par défaut.

Par honnêteté : les règles de craft sont exprimées avec des exemples TypeScript ; les patterns qu'elles encodent sont indépendants du langage.

La méthode

Six phases. Chacune sous gate.

Chaque phase a des conditions d'entrée et une Definition of Done. On n'avance pas sur affirmation : on avance sur preuve.

PhaseLivrableTerminée quand
1 · Cadrerframing.mdLe sponsor valide le critère de succès observable et le périmètre du plancher
2 · Architecturerarchitecture.md + ADRFrontières décidées, stack encore ouverte
3 · Livrer le plancherSystème qui tourne + floor.mdPremière preuve mesurée contre le critère, sur cas réels
4 · Itérer sur preuveIncréments + ADRChaque ajout tracé jusqu'à un déclencheur objectif
5 · Gouverner et évaluerThreat model, rubrique, observabilitéInstrumenté dès le jour zéro, jamais rattrapé après coup
6 · TransmettreKit de passationL'équipe refait une tâche en autonomie : démontré, pas déclaré

Aucune phase ne se ferme sans son artefact. Aucun gate ne se franchit sur affirmation. La phase 5 est transverse : elle démarre au jour zéro, pas après l'incident.

Là où les autres s'arrêtent

Compatibles en amont. Runward est la couche d'après.

Les frameworks pilotés par la spec sont bons sur ce qu'ils gardent. Runward commence là où leur dernier gate se ferme. Les plateformes commerciales (spec-driven dans l'IDE, spec comme source) règlent la question par le verrouillage ; Runward est MIT et agnostique en outillage.

S'arrête au code mergé

Spec Kit

Excellent pour garder la façon dont le logiciel s'écrit : constitution → specify → plan → tasks → implement. Un chemin discipliné de l'intention au code.

Runward : votre spec.md devient l'entrée de framing.md ; les gates continuent après le merge.

Délibérément sans gates rigides

OpenSpec

Excellent pour des specs légères, pilotées par le changement, en brownfield. Cette légèreté est une vertu quand on écrit le code, un passif quand on l'opère.

Runward : ajoute les gates exactement là où la preuve est exigée : preuve sur trafic réel, threat model, évaluation, passation.

Un persona ne répond pas devant un régulateur

BMAD

Excellent pour simuler une équipe agile au complet : douze personas IA et plus, chacun dans son rôle, le jugement distribué sur la troupe.

Runward : inverse le pari : un opérateur responsable, et l'agent exécute sous ses gates.

Gouvernance du merge, pas du système

Spec Kitty

Excellent pour gouverner la boucle de livraison : review → accept → merge, worktrees, un Kanban sur le flux des changements.

Runward : les gates continuent jusqu'en production : preuve sur trafic, threat model, boucle d'évaluation, passation.

L'opérateur

Un humain responsable. L'agent exécute sous ses gates.

Runward suppose une façon de travailler que la plupart des frameworks de code agentique ne supposent pas : un opérateur, embarqué côté métier, en binôme avec un agent de code. L'agent exécute les workflows, applique les règles de craft, rédige les artefacts, et ne franchit jamais un gate sur sa propre affirmation. L'opérateur tient chaque gate : il valide le critère de succès avec le sponsor, accepte ou refuse la preuve du plancher, décide chaque déclencheur de complexité, démontre la passation.

L'inversion fondatrice de la méthode (l'architecture contraint le modèle) appliquée au processus de livraison lui-même.

Les frameworks qui simulent une équipe distribuent le jugement entre des personas. En production, et doublement en secteur régulé, quelqu'un doit répondre du système. Un persona ne le peut pas.

Conçu pour le run régulé

La sécurité par l'architecture, pas par la détection.

  • Règle 2-sur-3 sur la fenêtre de contexteEntrée non fiable, données privées, actions externes : jamais les trois dans le même contexte. La triade létale est contrainte structurellement, pas filtrée heuristiquement.
  • Lectures fail-open, actions fail-closedUne lecture dégradée peut passer avec un avertissement. Une action dégradée ne part jamais.
  • Plafonds de coût dès le jour zéroLes plafonds budgétaires vivent dans la chaîne de middleware dès le premier commit, pas après la première facture.
  • Boucle d'évaluation avec juge ancré et hold-outTester le déterministe, évaluer le non-déterministe : contre une rubrique, pas au ressenti.
  • Passation prouvée par une tâche refaite seulLa mission se termine quand l'équipe qui reprend refait une tâche sans vous. Démontré, pas déclaré.
