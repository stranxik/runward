Your spec survived implementation. Will it survive production?

Runward is a delivery framework for agentic systems: floor first, evolution on evidence, governance from day zero, handover with proof. It picks up where spec-driven development stops.

Why · Four broken assumptions

Agentic systems break the rules classical engineering was built on.

Four assumptions of distributed engineering stop holding the day a model sits at the core of your system.

01

The core is non-deterministic

Same input, different output — by design. Testing built on repeatability no longer measures what matters.

02

Input is indistinguishable from instruction

Anything the model reads can try to command it. Prompt injection is structural, not a bug to patch.

03

Forgetting becomes engineering

Memory that only grows drowns the signal. Decay, invalidation and consolidation have to be designed, not hoped for.

04

The blast radius is unprecedented

An agent with tools acts on the world. A bad output is no longer just a bad answer.

What Runward is

Not an agent. Not a runtime.

Runward is a method made executable. Your existing spec becomes the input of runward/framing.md — and the gates continue from there.

  • 01

    A mission structure in markdown, living in your repo: framing, architecture, decisions, governance, runbook.

  • 02

    10 workflows executed by your coding agent — Claude Code, Cursor, Copilot, Gemini CLI, Windsurf, or anything that reads AGENTS.md.

  • 03

    48 craft rules the agent applies while building: memory scoring, tiered retrieval, event sourcing, multi-provider fallback, prompt-injection defenses.

  • 04

    A decision matrix of 22 arbitrations — each with one sober default and one explicit trigger. No trigger, no complexity.

  • 05

    A CLI that audits the gates: runward check tells you which deliverable, expected at which phase, is missing, started, or filled.

  • 06

    A clonable TypeScript reference floor — hexagonal core, model behind a port, middleware chain, day-zero cost ceiling. Zero keys, zero network by default.

Honesty note: the craft rules are expressed with TypeScript examples; the patterns they encode are language-agnostic.

The method

Six phases. Each one gated.

Every phase has entry conditions and a Definition of Done. You do not move on assertion; you move on evidence.

PhaseOutputDone when
1 · Frameframing.mdSponsor validates the observable success criterion and the floor scope
2 · Architectarchitecture.md + ADRsBoundaries decided, stack still open
3 · Ship the floorRunning system + floor.mdFirst measured proof against the criterion, on real cases
4 · Iterate on evidenceIncrements + ADRsEvery addition traced to an objective trigger
5 · Govern & evaluateThreat model, rubric, observabilityInstrumented from day zero, never retrofitted
6 · Hand overHandover kitThe team redoes a task autonomously — demonstrated, not declared

No phase closes without its artifact. No gate is crossed on assertion. Phase 5 is transverse: it starts at day zero, not after the incident.

Where the others stop

Compatible upstream. Runward is the layer after.

Spec-driven frameworks are good at what they gate. Runward starts where their last gate closes. Commercial platforms — IDE spec-driven, spec-as-source — solve this with lock-in; Runward is MIT and tool-agnostic.

Stops at merged code

Spec Kit

Great at gating how software gets written: constitution → specify → plan → tasks → implement. A disciplined path from intent to code.

Runward: your spec.md becomes the input of framing.md — the gates continue past the merge.

Deliberately no rigid gates

OpenSpec

Great at lightweight, change-driven specs for brownfield work. Its lightness is a virtue while writing code — and a liability while operating it.

Runward: adds the gates exactly where evidence is required — proof on real traffic, threat model, evaluation, handover.

A persona cannot answer to a regulator

BMAD

Great at simulating a full agile team: twelve-plus AI personas, each playing a role, judgment distributed across the cast.

Runward: inverts it — one accountable operator, and the agent executes under their gates.

Governance of the merge, not of the system

Spec Kitty

Great at governing the delivery loop: review → accept → merge, worktrees, a Kanban over the flow of changes.

Runward: the gates continue into production — proof on traffic, threat model, evaluation loop, handover.

The operator

One accountable human. The agent executes under their gates.

Runward assumes a way of working most agentic-coding frameworks do not: one operator, embedded on the business side, paired with a coding agent. The agent executes workflows, applies the craft rules, drafts artifacts — and never crosses a gate on its own assertion. The operator owns every gate: validates the success criterion with the sponsor, accepts or rejects the floor's proof, decides each complexity trigger, demonstrates the handover.

The method's founding inversion — the architecture constrains the model — applied to the delivery process itself.

Frameworks that simulate a team distribute judgment across personas. In production — and doubly so in regulated sectors — someone has to answer for the system. A persona cannot.

Built for the regulated run

Security by architecture, not detection.

  • 2-of-3 rule on the context windowUntrusted input, private data, external actions: never all three in the same context. The lethal trifecta is constrained structurally, not filtered heuristically.
  • Fail-open reads, fail-closed actionsA degraded read can pass with a warning. A degraded action never goes through.
  • Day-zero cost ceilingsBudget caps live in the middleware chain from the first commit, not after the first invoice.
  • Evaluation loop with anchored judge and hold-outTest the deterministic, evaluate the non-deterministic — against a rubric, not vibes.
  • Handover proven by a task redone aloneThe mission ends when the receiving team redoes a task without you. Demonstrated, not declared.
